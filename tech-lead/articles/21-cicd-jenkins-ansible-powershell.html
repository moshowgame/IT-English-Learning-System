CI/CD Pipeline — Jenkins + Ansible + PowerShell

Article 21 · Module 6: Engineering Automation · Tech Lead English

⏱ 9 min read 🟠 Intermediate 🎯 Jenkins builds, Ansible playbooks, PowerShell deployment, promotion gates, rollback

1. Scenario 场景背景

It is Monday, 9:30 AM HKT, and your squad is running the post-release review on Microsoft Teams. Friday's deployment of the Payment Gateway service to SIT failed — the Windows service never came up, and the release slipped to this week. You are the Tech Lead; joining are Raj, your senior developer (Bangalore), Lin, a backend developer who owns the build tooling (Hong Kong), and Sarah, your Scrum Master (London).

周一上午 9:30 香港时间，squad 在 Teams 上开发布复盘会。周五 Payment Gateway 服务部署到 SIT 失败——Windows 服务一直起不来，发布顺延到本周。你是 Tech Lead；参会的是高级开发 Raj（班加罗尔）、负责构建工具的后端开发 Lin（香港），以及 Scrum Master Sarah（伦敦）。

Your current pipeline: Jenkins builds and versions the artifact; an Ansible playbook manages environment config; but the Windows service deployment and smoke checks are still manual PowerShell steps. Your goal today: review the failure, and agree to automate the remaining manual steps — build once, promote the same artifact through DEV → SIT → UAT → PROD, with approval gates and a one-job rollback.

当前流水线：Jenkins 负责构建并给 artifact 打版本号；Ansible playbook 管理环境配置；但 Windows 服务部署和冒烟检查还是手工 PowerShell 步骤。今天的目标：复盘故障，并敲定把剩余手工步骤自动化——构建一次，同一 artifact 沿 DEV → SIT → UAT → PROD 一路晋升，带审批门禁和一键回滚。

2. Dialogue 英文对话

You (TL): Morning all. Quick post-mortem on Friday's SIT release — build 2.4.7. The artifact deployed, but the Windows service never came up: the health endpoint returned 503 and the service was stuck in "Starting". Smoke check failed, release slipped. 大家早上好。快速复盘一下周五的 SIT 发布——build 2.4.7。Artifact 部署上去了，但 Windows 服务一直起不来：健康检查端点返回 503，服务卡在"启动中"。冒烟检查失败，发布顺延。
Raj (Senior Dev): I dug into it over the weekend. Root cause: the config file on the SIT server was stale. Someone patched it manually two weeks ago during a hotfix, and it still points at the old message queue. The artifact was fine — the environment config wasn't. 我周末查了。根因：SIT 服务器上的配置文件过期了。两周前有人做 hotfix 时手工改过它，它还指向旧的消息队列。Artifact 本身没问题——问题出在环境配置。
You (TL): So this is classic config drift. DEV config is managed by the Ansible playbook — versioned, reviewed, repeatable. SIT is still configured by hand. Manual steps are where releases fail — not in the code, in the gaps between jobs. 这就是典型的配置漂移。DEV 的配置由 Ansible playbook 管理——有版本、有评审、可重复。SIT 还是手工配的。发布失败都败在手工步骤上——不是败在代码，是败在任务之间的缝隙里。
Lin (Dev): To be fair, the Jenkins side is solid. The pipeline compiles, runs the unit tests, versions the artifact 2.4.7-build-118, and pushes it to the artifact repository. The gap is everything after the artifact — deployment and verification are still a human with a PowerShell window. 客观说，Jenkins 这边是稳的。流水线编译、跑单测、给 artifact 打版本 2.4.7-build-118，推到 artifact 仓库。缺口在 artifact 之后的所有环节——部署和验证还是一个拿着 PowerShell 窗口的人。
You (TL): Agreed. My proposal: we wrap the manual PowerShell deployment script into the Ansible playbook, and trigger it from Jenkins as a proper deployment job. Build once, then promote the same artifact through DEV, SIT, UAT, PROD — no rebuilds between environments, no re-compilation surprises. 同意。我的提案：把手工的 PowerShell 部署脚本收编进 Ansible playbook，由 Jenkins 以正式部署任务触发。构建一次，然后同一个 artifact 沿 DEV、SIT、UAT、PROD 一路晋升——环境之间不重新构建，没有重新编译带来的意外。
Raj (Senior Dev): The PowerShell script does three things today: stops the old service, installs the new artifact as a Windows service, and starts it. I'd add smoke checks to the same run: Get-Service for the status, an Invoke-WebRequest against the /health endpoint, and a tail of the startup log for errors. Exit non-zero and the pipeline goes red. PowerShell 脚本现在做三件事：停旧服务、把新 artifact 装成 Windows 服务、启动。我建议在同一次运行里加冒烟检查：Get-Service 看状态，Invoke-WebRequest 打 /health 端点，再 tail 启动日志找错误。退出码非零，流水线就标红。
You (TL): And it has to be idempotent. Run the playbook twice — same input, same state. No half-installed service, no duplicate config entries. Ansible gives us that for free on the config side; the PowerShell steps need explicit check-then-act logic. 而且必须幂等。Playbook 跑两遍——同样输入，同样状态。不能装一半，不能出现重复配置。Ansible 在配置侧天然幂等；PowerShell 步骤需要显式的先检查再执行逻辑。
Sarah (SM): Quick question from the process side — do we auto-deploy all the way to production? Product will ask me today. 流程上快速问一句——我们要一路自动部署到生产吗？Product 今天就会问我。
You (TL): No. SIT promotes automatically when the pipeline is green. UAT promotion needs QA sign-off — that's an approval gate in the Jenkins pipeline, a pause for a human decision. PROD needs the CAB-approved change ticket plus my approval as TL. The gates stay; the manual toil goes. And if a release goes wrong — rollback is redeploying the last-known-good artifact with the same playbook. Config is versioned in the repo, artifacts are pinned by version. Rollback becomes a pipeline job, not a firefighter with a laptop at 11pm. 不。SIT 在流水线绿了之后自动晋升。UAT 晋升需要 QA 签批——这是 Jenkins 流水线里的一个审批门禁，停下来等人做决定。PROD 需要 CAB 批准的变更单加上我作为 TL 的审批。门禁保留，手工苦力消失。如果发布出问题——回滚就是用同一个 playbook 重新部署上一个已知良好版本。配置在仓库里有版本，artifact 按版本固定。回滚变成一个流水线任务，而不是深夜 11 点抱着笔记本救火。
Raj (Senior Dev): One more thing before we commit — credentials. Right now the service account password is in a text file on the team share. That has to move to the Jenkins credentials store and Ansible Vault this sprint, or InfoSec will flag it in the next audit. 开工前还有一件事——凭据。现在服务账号密码躺在团队共享盘的一个文本文件里。这个 Sprint 必须挪进 Jenkins credentials store 和 Ansible Vault，否则 InfoSec 下次审计一定会标出来。
You (TL): Agreed — and that one is non-negotiable. Actions: Lin wraps the PowerShell steps into the playbook with idempotent checks; Raj builds the smoke-check job; credentials move into the vault; Sarah, we'll demo the fully automated SIT deployment to the squad on Friday. Next release should be a button push, not a ritual. 同意——这条没得商量。行动项：Lin 把 PowerShell 步骤收编进 playbook 并加幂等检查；Raj 搭冒烟检查任务；凭据迁入 vault；Sarah，周五我们向 squad 演示全自动的 SIT 部署。下次发布应该是按一个按钮，而不是举行一场仪式。
Sarah (SM): Perfect. I'll tell the PM the release is becoming boring — that's a compliment in my vocabulary. 太好了。我会告诉 PM，发布正在变得无聊——在我的词典里这是夸奖。

3. Key Phrases 关键句型

  • CORE Smoke check failed, release slipped. 冒烟检查失败，发布顺延。 Smoke check = 上线后的快速健康验证。Pair the failure with the consequence — TLs report cause and impact in one breath. 冒烟检查失败要连带后果一起说。
  • CORE This is classic config drift. 这是典型的配置漂移。 "Classic X" names the pattern, not the person. It turns an incident into a known category — and a known category has a standard fix. 用"经典 X"给问题归类，指问题不指人。
  • CORE Manual steps are where releases fail. 发布失败都败在手工步骤上。 The TL's thesis sentence for automation. Short, general, memorable. Follow it with evidence, not opinion. 自动化议题的核心论点句，短而有力，后接证据。
  • CORE Build once, promote the same artifact through DEV, SIT, UAT, PROD. 构建一次，同一 artifact 沿 DEV、SIT、UAT、PROD 晋升。 "Promote" is the standard verb for moving a build across environments. Build-once is the golden rule — rebuilds introduce drift. Promote 是跨环境晋升的标准动词。
  • FORMAL UAT promotion needs QA sign-off — that's an approval gate in the pipeline. UAT 晋升需要 QA 签批——这是流水线里的审批门禁。 Approval gate = 停下来等人工审批的门禁。Frame gates as deliberate pauses, not delays: "a pause for a human decision". 门禁是刻意停顿，不是拖延。
  • CORE It has to be idempotent — same input, same state. 必须幂等——同样输入，同样状态。 Idempotent = 跑多少遍结果都一样。The pocket definition "same input, same state" works even with non-technical stakeholders. "同样输入同样状态"是对非技术方也好用的口袋解释。
  • CORE Rollback is redeploying the last-known-good artifact with the same playbook. 回滚就是用同一个 playbook 重新部署上一个已知良好版本。 Last-known-good = 最近一次验证成功的版本。Define rollback as a routine job, not an emergency ritual — that's how you sell automation. 把回滚定义为日常任务而非紧急仪式。
  • CORE The gates stay; the manual toil goes. 门禁保留，手工苦力消失。 Balanced "X stays, Y goes" construction. Perfect for reassuring auditors while selling automation — you automate the work, never the control. 自动化工作而非自动化管控，审计最买账。
  • CASUAL Next release should be a button push, not a ritual. 下次发布应该是按一个按钮，而不是举行一场仪式。 Contrast metaphor — great for closing an automation pitch. "Ritual" hints at superstition; "button push" hints at boring reliability. 收尾金句："仪式"暗指玄学，"按按钮"暗指可靠。
  • FORMAL We demo the fully automated SIT deployment on Friday. 周五我们演示全自动的 SIT 部署。 Commit to a demo date when pitching automation — a deadline converts intention into a sprint plan. 承诺演示日期，把意向变成 Sprint 计划。

4. Vocabulary 词汇表

  • Pipeline n. 流水线 The automated chain from code commit to deployment — build, test, deploy, verify. In Jenkins, defined as code in a Jenkinsfile.
  • Artifact n. 构件 / 产物 The versioned output of a build (e.g., 2.4.7-build-118) stored in an artifact repository and promoted across environments unchanged.
  • Jenkins job n. Jenkins 任务 A unit of automation in Jenkins — build job, deployment job, smoke-check job — triggered manually, by webhook, or downstream.
  • Playbook n. (Ansible) 剧本 An Ansible automation file describing desired state across servers — config files, packages, services — run against an inventory of hosts.
  • Idempotent adj. 幂等的 Running the same automation twice produces the same state — no duplicates, no partial installs. The core property of good Ansible/PowerShell automation.
  • Config drift n. 配置漂移 When an environment's actual config diverges from the version-controlled config, usually through manual changes. A top cause of "it worked in DEV".
  • Smoke test / smoke check n. 冒烟测试 A fast post-deployment verification — service status, health endpoint, log probe — to confirm the system is up before deeper testing.
  • Promotion n. 晋升 / 环境晋级 Moving the same verified artifact from one environment to the next (DEV → SIT → UAT → PROD) without rebuilding it.
  • Approval gate n. 审批门禁 A pipeline pause requiring a human decision (QA sign-off, CAB ticket, TL approval) before promotion continues.
  • Rollback n. 回滚 Returning an environment to the last-known-good version after a failed release — ideally by redeploying, not by manual repair.
  • Last-known-good adj. 上一个已知良好的 The most recent artifact plus config combination that passed all checks. The target version for any rollback.
  • Credential vault n. 凭据保管库 Centralized secret storage — Jenkins credentials store, Ansible Vault — replacing passwords in scripts, text files, and chat messages.

5. Grammar Notes 语法点

① "Failed at / stuck in / slipped" — narrating a failed release

Post-mortems use precise stage verbs: the build passed, the deploy failed, the service was stuck in "Starting", the release slipped. Match the verb to the stage — never just say "it broke".

复盘要用精确的阶段动词：build 过了、deploy 失败、服务卡在 Starting、发布顺延。动词要匹配阶段，别只说"挂了"。

  • ✅ "The build passed; the deploy failed at the config step; the service was stuck in Starting."
  • ❌ "It broke somewhere on Friday."

② "Has to be + past participle" — automation mandates

Non-negotiable requirements use has to be + adjective/participle. Compare with softer should — save it for suggestions.

硬性要求用 has to be；建议性的才用 should。

  • ✅ "It has to be idempotent." / "Credentials have to be vaulted." / "The artifact has to be pinned by version."
  • ❌ "It should probably be idempotent, ideally."

③ "X stays; Y goes" — the balanced trade

Selling automation means removing work, not removing control. The semicolon construction is symmetric and quotable — ideal for summaries and slide headers.

推销自动化要表明"去工作、不去管控"。分号对仗结构适合总结和幻灯片标题。

  • ✅ "The gates stay; the manual toil goes."
  • ✅ "The approvals stay; the runbooks go."

6. Cultural Tips 文化 / 职场 Tips

💡 Demoing automation wins to stakeholders
  1. Demo the pipeline, not the slide deck. A live "trigger SIT deployment → watch smoke checks go green in 6 minutes" beats ten slides. Show the button push.
  2. Quantify before and after. "Deployment: 90 manual minutes → 6 automated minutes; config drift incidents this quarter: 4 → 0." Numbers are the stakeholder language.
  3. Frame boring as success. "Our releases are becoming boring" is a compliment — no heroics, no 11pm firefighting. Heroes are a symptom of manual pipelines.
  4. Give credit to the team. "Lin wrapped the PowerShell into the playbook; Raj built the smoke checks." Automation wins are squad wins — TLs who hoard credit lose engineers.
⚠️ Credential handling — say it early, say it loudly
  • ❌ "The password is in the readme on the share — just look it up." This is an audit finding and, in a bank, potentially a disciplinary matter.
  • ✅ "Secrets live in Ansible Vault / the Jenkins credentials store — scripts reference them, humans never see them."
  • ❌ Pasting credentials in chat, tickets, or emails "just for the release". Chat history is forever.
  • ✅ Raise credential hygiene yourself before InfoSec finds it — a self-reported fix builds trust; an audit finding costs credibility.
✅ Pushing back when asked to skip quality gates

When a PM says "Can we skip the UAT gate this time? The business needs it today" — don't argue emotionally. Answer with the trade:

"We can go today, and the rollback path is one job — but if we skip the gate and it breaks in PROD, we explain the incident to the regulator. I recommend we hold the gate and go tomorrow morning."

You offered speed, you named the risk, you kept the decision documented. Gates are the cheapest insurance the bank buys.

7. Practice 练习题

✍️ Practice Drills
Q1. Translate the automation pitch into English:

"复盘一下：周五的 SIT 发布失败，冒烟检查没过。根因是配置漂移——SIT 的配置还是手工改的。提案：把 PowerShell 部署步骤收编进 Ansible playbook，构建一次，同一 artifact 沿 DEV、SIT、UAT、PROD 晋升。UAT 加 QA 签批门禁，PROD 需要 CAB 变更单。回滚就是用同一个 playbook 重部上一个已知良好版本。凭据全部迁入 vault。"

"Quick post-mortem: Friday's SIT release failed — the smoke check didn't pass. Root cause was config drift — the SIT config was still changed manually.

Proposal: we wrap the PowerShell deployment steps into the Ansible playbook, build once, and promote the same artifact through DEV, SIT, UAT and PROD. UAT gets a QA sign-off approval gate; PROD needs the CAB-approved change ticket.

Rollback is redeploying the last-known-good artifact with the same playbook. And all credentials move into the vault."

Q2. Fill in the pipeline terms:

"(1) Jenkins compiles and versions the ____ (artifact). (2) The Ansible ____ manages environment config. (3) The deployment must be ____ — same input, same state. (4) DEV config is fine; SIT suffered ____ drift. (5) After deploy we run a ____ check: Get-Service status plus a call to /health. (6) UAT promotion requires QA sign-off — an approval ____ in the pipeline. (7) If PROD breaks, we redeploy the last-known-____ artifact. (8) Passwords live in the Jenkins credentials ____ / Ansible Vault."

(1) artifact / (2) playbook / (3) idempotent / (4) config / (5) smoke / (6) gate / (7) good / (8) store

Q3. Role-play: explain the promotion path to an auditor

An auditor asks: "How does code get to production, and who can skip a gate?" Explain in spoken English: (a) the promotion path and artifact strategy, (b) each gate and its approver, (c) the rollback mechanism, (d) how secrets are handled.

"Happy to walk you through it. We build once in Jenkins — the artifact is versioned and pushed to the artifact repository, and the same artifact is promoted through DEV, SIT, UAT and PROD — nothing is rebuilt between environments.

Promotion to SIT is automatic when the pipeline is green, including the smoke checks — service status, health endpoint, startup log. UAT promotion pauses at an approval gate for QA sign-off. PROD requires the CAB-approved change ticket plus TL approval — no gate can be skipped; even emergency changes go through eCAB and are reviewed afterwards.

Rollback is redeploying the last-known-good artifact with the same Ansible playbook — config is versioned, so a rollback is a routine job, not a manual repair.

And credentials live in the Jenkins credentials store and Ansible Vault — scripts reference them; nobody holds passwords in files or chat. Everything is traceable in the Jenkins build history and the change tickets."

8. Key Takeaways 本篇要点

🎓 What you can now say as TL
  1. Diagnose a failed release in pipeline vocabulary — artifact, smoke check, config drift, last-known-good.
  2. Sell the automation trade — "build once, promote the same artifact"; "the gates stay; the manual toil goes".
  3. Define the gates precisely — SIT automatic, UAT needs QA sign-off, PROD needs CAB plus TL approval.
  4. Make rollback boring — same playbook, pinned versions, one job.
  5. Protect credentials — vault first, audit-proof always.

Practice tip: In your next release review, use one pipeline term naturally — e.g., "That's config drift; the playbook will absorb it." Real usage is the fastest path to fluency.
