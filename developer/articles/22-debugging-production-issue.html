Debugging a Production Issue

Article 22 · Module 6: Production Support & Debugging · Developer English

⏱ 10 min read 🟠 Intermediate — hands-on walkthrough 🎯 Correlation IDs · Splunk · Data fix & backfill · RCA

1. Scenario 场景背景

It is the next morning, 10:00 AM HKT. Yesterday's Sev2 incident INC3345 (payment file upload failures) was stabilised with a workaround, and the service is limping along. Now the real work begins: finding the root cause and fixing it properly.

第二天上午10点（香港时间）。昨天的 Sev2 事件 INC3345（付款文件上传失败）已用临时方案稳住，服务勉强可用。 现在要做真正的工作：找到根因并彻底修复。

You (Wei) have spent the morning pulling logs from Splunk using correlation IDs, comparing file timestamps, and reproducing the failure in dev with production-like data. You now walk Priya (Tech Lead, UK) through your findings, discuss fix options (hotfix vs next release), and agree on preventive actions and the RCA document.

Good debugging English is short, factual and verifiable: what you searched, what you found, what it means, and what you propose next.

排查场景的英语表达要简短、基于事实、可验证：查了什么、发现了什么、说明什么、下一步建议什么。

你（Wei）花了一上午用关联 ID 在 Splunk 中检索日志、对比文件时间戳， 并在开发环境用类生产数据复现了故障。现在你向技术负责人 Priya（英国）讲解发现， 讨论修复方案（紧急热修复 vs 纳入下一次发布），并就预防措施和 RCA 文档达成一致。

3. Key Phrases 关键句型

  • CORE I've found the root cause — do you have ten minutes for a walkthrough? 我找到根因了——你有十分钟听我过一遍吗？ Walkthrough = 逐步讲解. Always offer a time-boxed walkthrough, not a wall of text. 提出一个有时限的讲解请求，比甩一大段文字更专业。
  • CORE I pulled the logs using the correlation ID, one search per transaction. 我用关联 ID 拉取日志，每笔交易查一次。 Pull the logs = 拉取日志. Mentioning your method (correlation ID) shows the finding is evidence-based. 说明方法（关联ID）让结论显得有据可查。
  • CORE All the errors cluster between 09:40 and 09:52. 所有错误集中在 09:40 到 09:52 之间。 Cluster = 聚集在. A time window is the fastest way to link errors to an event. 给出时间窗是把错误和事件关联的最快方式。
  • CASUAL It turns out to be a data issue, not a code defect. 结果证明是数据问题，不是代码缺陷。 It turns out to be… = 结果是…… 用于从假设到结论的时刻。Also: "the evidence points to a data issue".
  • FORMAL I reproduced it with production-like data, so it's confirmed rather than a hypothesis. 我用类生产数据复现了，所以这是已验证的结论，不是推测。 Production-like data = 类生产数据（脱敏后的真实数据）. Tech leads always ask: reproduced or hypothesis? 技术负责人必问：复现了还是猜测？
  • FORMAL We can hotfix tonight, or fold the change into next week's scheduled release. 我们可以今晚热修复，或者把改动纳入下周的例行发布。 Fold into a release = 并入发布列车. Presenting two options + a recommendation is how devs escalate decisions. 给选项加推荐，是开发汇报决策的标准方式。
  • CORE I'll apply a data fix and backfill the failed records in tonight's change window. 我会在今晚的变更窗口内执行数据修复并回补失败记录。 Always pair a data fix with when (change window) and approval. 数据修复必须带上时间和审批信息。
  • FORMAL CHG88210 is with the change approver, with a rollback plan attached. 变更单 CHG88210 正在审批人那里，已附回滚方案。 No rollback plan = no approval in HSBC process. Attach it upfront. 在汇丰流程里，没有回滚方案就拿不到审批，要提前附上。
  • CORE Preventive action: add input validation plus an alerting rule if the error count spikes. 预防措施：增加输入校验，并加一条错误数飙升的告警规则。 Every RCA ends with preventive actions — make them concrete and assignable. RCA 必须落到具体、可指派的预防措施。
  • FORMAL I'll share the RCA draft before Thursday's review — keeping it factual and no-blame. 我会在周四复盘会前发出 RCA 草稿——保持客观、不追责。 Keeping it factual = 只讲事实. Signalling tone upfront sets expectations for the meeting. 提前表明基调，给会议定好预期。

4. Vocabulary 词汇表

  • correlation ID n. 关联 ID / 追踪 ID 把一笔交易在各系统、各服务的日志串起来的唯一编号。"search by correlation ID" 是排查的第一把钥匙。
  • Splunk HSBC 日志聚合检索平台 银行最常用的日志工具，按 index、sourcetype、时间范围检索。"run a Splunk query" = 跑一条日志查询。
  • Kibana n. 日志检索可视化工具（Elasticsearch） 功能定位与 Splunk 类似，基于 ELK 栈。面试常问 "Splunk vs Kibana"，回答要点：检索语法和生态不同，排查思路一致。
  • reproduce /ˌriːprəˈdjuːs/ v. 复现（故障） 用相同数据和步骤让问题再次发生。"reproduced with production-like data" = 用类生产数据复现。复现是把假设变成结论的一步。
  • data fix n. 数据修复 不改代码，直接修正错误数据（UPDATE/DELETE/INSERT）。必须走变更流程："the data fix is approved under CHG88210".
  • backfill /ˈbækfɪl/ v. & n. 回补 / 补数 把之前处理失败的记录重新处理，保证数据完整。"backfill the 118 failed records" = 回补118条失败记录。
  • hotfix /ˈhɒtfɪks/ n. 紧急修复（热修复） 绕过正常发布节奏的快速代码修复，风险高、审批严。"a hotfix bypasses the release train".
  • rollback /ˈrəʊlbæk/ n. & v. 回滚 修复失败时退回原状态（代码回退或数据还原）。"rollback plan" 回滚方案是变更单的必备附件。
  • change window HSBC 变更窗口 获批的生产变更执行时段，通常在业务低峰期（如周末深夜）。"run it inside the change window" = 只在窗口内执行。
  • RCA (root cause analysis) n. 根因分析（报告） 事件结案文档，四个固定板块：timeline 时间线、root cause 根因、contributing factors 促因、preventive actions 预防措施。
  • post-mortem / no-blame review n. 复盘会（无指责复盘） 事件后的团队复盘会议。No-blame 原则：对事不对人，聚焦流程与系统改进，不追究个人责任。
  • preventive action n. 预防措施 防止问题复发的改进项：输入校验、告警规则、监控看板、流程检查清单等。RCA 的落脚点。

5. RCA Document & Safe Data Fixes RCA 文档与安全数据修复

① Debug workflow checklist 排查五步法

  • 1. Scope it. Pick one failed transaction and grab its correlation ID — one example beats a thousand errors.
  • 2. Pull the logs. Splunk/Kibana query filtered on the service + correlation ID + time window; note the exact error text ("invalid delimiter").
  • 3. Compare before/after. What changed? Last deployment? Last inbound file? Last upstream release? Timestamps tell the story.
  • 4. Reproduce. Re-run the failure with production-like data in a lower environment; classify: data issue vs code defect vs environment.
  • 5. Propose the fix. Present options (hotfix vs next release, data fix vs code change) with risks and a recommendation.

第 2 步的示例 Splunk 查询（按服务、错误级别、时间窗过滤，再用关联 ID 定位单笔交易）：

index=pay_app sourcetype=payment-upload "ERROR" earliest=11/15/2026:09:30:00 latest=11/15/2026:10:00:00 | search correlationId=PAY-20261115-004412

Kibana 上的等价做法是用 KQL 过滤 correlationId 字段并锁定时间范围——工具不同，思路一致。

常见误区 common pitfalls：

  • ❌ Searching errors without a time window — you drown in unrelated noise from other services.
  • ❌ Reading logs backwards from the latest error — start from the first failure and the event right before it.
  • ❌ Debugging only in your head — reproduce it first, then you can prove it.

② RCA document structure RCA 文档四板块（以 INC3345 为例）

  • Timeline: 09:38 inbound file lands → 09:40 first validation failure → 09:45 Sev2 opened, bridge called → 10:05 workaround communicated → 22:35 data fix & backfill completed → 22:40 resolved.
  • Root cause: the upstream file feed switched from pipe-delimited to comma-delimited format without notification.
  • Contributing factors: no input validation on delimiters or duplicate transaction references; no alerting on validation error spikes; upstream release not communicated to downstream teams.
  • Preventive actions: (1) loader rejects unknown delimiters with a clear error and an alert; (2) monitoring rule on validation-error count; (3) upstream release-notification checklist agreed with the upstream team.

③ Safe backfill rules 安全补数守则

  • Never touch production data ad hoc. Every data fix needs a change record (CHG-xxxxx), an approver, and an approved change window.
  • Backup before you fix. Export the affected rows first — your rollback plan is only as good as your backup.
  • Count before, count after. "118 failed records selected / 118 rows updated / 0 rows remaining" — verify with SQL counts, not eyeballing.
  • Script it, don't hand-edit. A reviewed, version-controlled script is auditable; a console update is not.

④ Post-fix verification 修复后验证

  • Row counts match: selected = updated = expected (118 selected / 118 updated / 0 remaining).
  • End-to-end re-run: let the next inbound file process and confirm success with the service desk and Ops.
  • Attach evidence to the change record (screenshots, query outputs) before closing CHG88210 — auditors will ask.

⑤ Hotfix or next release? 修复路径决策参考

  • Choose a hotfix when: users stay blocked until the next scheduled release (a week or more), and the change is small, well-tested and low-risk.
  • Choose the next release when: a data fix or workaround already unblocks users, or the code change is large and needs full regression testing.
  • The combo used here: data fix + backfill tonight to unblock users; the code fix rides next week's scheduled release.
  • The deciding question: "What's the customer impact of waiting?" —— 由业务影响决定路径，而不是个人偏好。

⑥ RCA writing: say this, not that RCA 措辞对照

  • ❌ "Sam forgot to add validation." → ✅ "The loader had no input validation on delimiters." — review the system, not the person.
  • ❌ "The upstream team broke it again." → ✅ "The upstream file format changed without downstream notification." — process gap, not blame.
  • ❌ "Nobody monitors this." → ✅ "No alerting rule existed on validation error counts." — an observable gap, not an accusation.

The golden rule of RCA writing: a reader who was never on the bridge should be able to retell the whole story — complete timeline, every claim backed by a log line or a screenshot.

RCA 写作的黄金法则：让没参与故障的人读完也能复述整个事件——时间线完整，每个结论都有日志或截图支撑。

6. Grammar Notes 语法点

① Present perfect vs past simple 汇报发现时的时态切换

Announcing news now → present perfect; giving the finished-time detail → past simple. The dialogue uses both in sequence:

  • ✅ "I've found the root cause." (news, no time given) → "I found it at 09:52 this morning." (finished time)
  • Time-stamped facts stay in past simple: "The errors clustered between 09:40 and 09:52."
  • ❌ "I have found it yesterday." — never mix a finished time with present perfect.

② "so" — linking evidence to conclusion 用 so 把证据推向结论

  • ✅ "The upstream switched the delimiter, so it's a data issue rather than a code defect."
  • Alternatives: "which means…", "that suggests…", "the evidence points to…".
  • Hedge only when you truly cannot conclude yet: "the initial signals suggest a data issue — verifying now."

③ Sequencing a fix plan 修复计划的时间连接词

  • First / then / after that / finally: "First I'll take a backup, then run the backfill script, after that we verify the counts."
  • once / as soon as + present simple (NOT will): "Once the change is approved, I'll run it inside the window." — ❌ "once the change will be approved".
  • by + time: "I'll share the RCA draft by Wednesday noon" = 不晚于周三中午。

7. Cultural Tips 文化/职场 Tips

🔍 Present Findings With Evidence 用证据讲发现
  • Narrate the method, then the finding: "I searched Splunk by correlation ID… the errors cluster after 09:38…" — method first makes conclusions credible.
  • Share the actual log line / query link in the channel, not just your summary — reviewers love verifiable evidence.
  • Distinguish fact from hypothesis: say "confirmed" only after reproduction; before that, say "working hypothesis".
  • Time-box the walkthrough. "Ten minutes, top three findings" respects everyone's calendar — the details live in the RCA doc.
⚠️ Data Fixes Without Approval = Career Risk 绕过审批改生产数据是职业红线
  • ❌ Fixing data directly on a Friday night "because users are blocked" — even with good intentions, this is an audit finding.
  • ✅ Raise the change record, get approval, run it in the window, keep evidence. If truly urgent, ask Ops to expedite the approval, never skip it.
  • 同场景中文常说“先改了再说”；在银行环境里，正确说法是 "Let me raise an emergency change"（走紧急变更），而不是直接动手。
  • 紧急路径也存在：emergency change（紧急变更）仍需审批与记录——走 fast track，不是 no track。
🤝 No-Blame Culture in Post-Incident Reviews 无指责复盘文化
  • Say "the loader had no input validation", never "Sam forgot to add validation" — review the system, not the person.
  • "Contributing factors" deliberately replaces "who was at fault" — multiple small gaps combine into one incident.
  • Thank the responders on the record: "Good catch by the on-call — the bridge was stood up within 10 minutes." Appreciation in writing builds the team.
  • 中文的“追责/背锅”文化在跨国银行复盘会上是大忌——用 lessons learned（经验教训）替代 blame（指责）。
  • End reviews with actions, not feelings. Every preventive action gets an owner and a date — that's what "lessons learned" means in practice.
