Production Support Basics

Article 21 · Module 6: Production Support & Debugging · Developer English

⏱ 10 min read 🟠 Intermediate — real incident scenario 🎯 Sev levels · Incident bridge · Triage · Status updates

1. Scenario 场景背景

It is 09:35 AM HKT on a Tuesday morning. You are a backend developer on the HSBC Payments team, and this week you are the on-call developer for your service — the corporate payment file upload service on HSBCnet.

周二上午9点35分（香港时间）。你是汇丰支付团队的后端开发工程师，本周轮到你担任 企业付款文件上传服务的值班开发（on-call）。

Your pager suddenly fires: the Ops team (Marcus, from the NOC in Kuala Lumpur) has opened a Sev2 incident — corporate users in Hong Kong and Singapore cannot upload payment files. Priya (your Tech Lead, UK), Amanda (Service Desk, Hong Kong) and Helen (BA, Hong Kong) are joining the incident bridge.

告警突然响起：运维团队（吉隆坡NOC的Marcus）开出了一个 Sev2 事件——香港和新加坡的企业用户无法上传付款文件。 技术负责人 Priya（英国）、服务台 Amanda（香港）和业务分析师 Helen（香港）即将加入故障应急会议。

Your job in the first 15 minutes: acknowledge the page, join the bridge, assess the impact, triage the category (code bug? data issue? environment problem? upstream system?), offer a workaround, and post the first status update to users.

你在前15分钟要做的事：确认告警、加入应急会议、评估影响面、给问题归类 （代码缺陷？数据问题？环境问题？上游系统问题？），提供临时解决方案，并向用户发布第一次状态更新。

3. Key Phrases 关键句型

  • CORE Acknowledged — I'm acknowledging the page and joining the bridge now. 收到——我正在确认告警，马上加入应急会议。 First words on any incident. Acknowledge fast, even if you have nothing to say yet. 故障响应的第一句话：先确认，再行动。
  • CORE First question: who's impacted, and since when? 第一个问题：影响面有多大，从什么时候开始的？ Impact + timeframe is the first thing every incident commander asks. 影响范围和时间点是事件响应的第一要素。
  • CORE Impact: … Cause under investigation: … Next update in 30 minutes. 影响：…… 原因调查中：…… 30分钟后提供下一次更新。 The standard 3-part status update template. Memorize it — you'll use it under pressure. 标准三段式状态更新模板，建议背下来。
  • CORE Let's triage: is it code, data, environment, or upstream? 我们来分类排查：代码、数据、环境，还是上游系统？ The 4-way triage question. Asking it out loud keeps the bridge focused. 四向分类法，让应急会议聚焦不发散。
  • FORMAL Last deployment was ten days ago, so I'm ruling out a recent code change. 最后一次部署是十天前，所以可以先排除近期代码变更。 Rule out = eliminate a possibility with evidence. Always justify it. 用证据排除可能性，要说明理由。
  • CASUAL It looks like a data issue rather than a code bug. 看起来是数据问题，而不是代码缺陷。 Rather than makes the contrast polite and evidence-based. 用 rather than 让对比显得客观、有依据。
  • CORE Can we offer users a workaround while we confirm the root cause? 在确认根因之前，能不能先给用户提供临时方案？ Workaround first, root cause second — restoring service beats finding the bug. 先恢复业务，再找根因。
  • FORMAL If the next file also fails, I'll escalate to the upstream team formally. 如果下一个文件也失败，我会正式向上游团队升级上报。 Formally signals an official escalation path with tickets — not just a chat message. 表示走正式上报流程，不是私下打招呼。
  • FORMAL Please raise tickets through the service desk so we can track the full impact. 请统一通过服务台提交工单，方便我们统计完整影响面。 Directing users to the service desk keeps impact counts accurate for the incident record. 引导用户走服务台，保证影响统计准确。
  • CORE I'll hand over to the APAC on-call at 6 PM with a written summary. 下午6点我会带书面总结交接给亚太区值班同事。 Hand over = pass the incident to the next shift. Always do it in writing. 交接班要书面化，避免信息丢失。

4. Vocabulary 词汇表

  • on-call /ɒn kɔːl/ adj. 值班的 / 待命的 轮到你响应生产故障。"I'm on-call this week" = 我这周值班。On-call 通常按周轮换（rotation），有补偿或调休。
  • page / paging /peɪdʒ/ v. & n. 呼叫值班人员 / 告警通知 通过 PagerDuty、OpsGenie 等工具向值班人推送紧急告警。"I got paged at 2 AM." = 我凌晨两点被告警叫醒。名词形式 a page。
  • incident bridge n. 故障应急会议（桥） 重大故障时专设的电话/Teams 会议，各角色实时在线。"Join the bridge" = 加入应急会。桥上保持安静纪律：只说结论和事实。
  • Sev1 / Sev2 / Sev3 HSBC 严重级别 1 / 2 / 3（Severity） Sev1 = 核心服务中断、重大客户影响、无临时方案；Sev2 = 主要功能降级但有临时方案；Sev3 = 小范围、影响有限，工作时间处理即可。
  • triage /ˈtriɑːʒ/ v. & n. 分类排查 / 判定问题类别 源自医疗分诊。开发语境下指快速判定问题属于 code / data / environment / upstream 哪一类，并确定优先级。
  • impact /ˈɪmpækt/ n. 影响（面） 多少用户、多少交易、哪些地区受影响。"What's the customer impact?" 状态更新必须先讲 impact。
  • workaround /ˈwɜːkəraʊnd/ n. 临时解决方案 / 绕行方案 让用户先能干活的办法，不等于修复（fix）。"interim workaround" = 临时过渡方案。
  • escalate / escalation /ˈeskəleɪt/ v. / n. 升级上报 / 上报流程 自己搞不定或需要更高权限/其他团队介入时走正式流程。"follow the escalation path" = 按升级路径上报，不是越级吵架。
  • service desk HSBC 服务台 / IT服务台 用户报障第一入口，在 ServiceNow 里登记工单（ticket）。They triage user reports and track impact counts.
  • incident commander (IC) n. 故障指挥官 重大故障中负责指挥协调、控制沟通节奏和决策的角色，不一定是最资深的人。"Who's the IC?"
  • handover /ˈhændəʊvər/ n. （值班）交接 跨时区团队必做：交班前写书面总结（现状、下一步、联系人），"handover notes" 交接纪要。
  • on-call rota / rotation n. 值班轮换表 团队轮流承担 on-call 的排班表。"It's your turn on the rota next week." 交班时用 handover notes 把在办事件逐条说清楚。

5. Triage Guide & Severity Levels 分级排查与严重级别

① Triage decision guide 四向分类排查法

  • Code bug 代码缺陷: started right after a deployment; reproducible in dev; stack traces point to your own code. Key question: "When did we last deploy to production?"
  • Data issue 数据问题: only specific records or files fail; the service itself is healthy; errors follow the data, not the release. Key question: "Is it every record, or specific ones?"
  • Environment / infra issue 环境/基础设施问题: timeouts, connection refused, disk full, memory pressure; no recent code change; several services affected at once. Key question: "Are other services on the same host affected?"
  • Upstream / downstream issue 上下游系统问题: your code is unchanged but the input changed; failures correlate with another team's release or file. Key question: "Did the upstream team run a release this weekend?"

技巧：先用一个问题排除两类，再集中验证剩下两类——这正是对话里 Priya 那句 "is it code, data, environment, or upstream?" 的用法。

One more habit worth building: write the triage conclusion down on the incident ticket — "Ruled out code change (last deploy 10 days ago); data issue suspected" — so late joiners don't repeat the same questions.

养成一个好习惯：把排查结论写进事件工单（如“已排除近期代码变更；疑似数据问题”）， 让后加入应急会的人不必重复提问。

② Severity definitions 严重级别定义（典型银行实践）

  • Sev1 (Critical) — Core service down or at risk, major client impact, no workaround. All-hands on the bridge, incident commander assigned, status updates every 30 minutes, management notified.
  • Sev2 (High) — Major function degraded but a workaround exists, or impact is limited to one region/product. Status updates every hour, bridge opened if diagnosis needs multiple teams.
  • Sev3 (Medium/Low) — Minor issue, few users affected, workaround available. Handled in business hours, daily update on the ticket is enough.

注：级别由 impact（影响面）和 urgency（紧急度）共同决定；宁可先定高一级，之后可以降级（downgrade），很难升级追认。

③ Template A — First update (within 15–30 minutes) 首次状态更新模板

"Impact: payment file upload is failing for corporate users in HK and SG since 09:15 HKT (~40 users, ~120 transactions queued). Cause under investigation: we are checking this morning's inbound file feed. Workaround: available via the service desk. Next update in 30 minutes."

④ Template B — Follow-up update 后续更新模板

"Update 10:20 HKT: Root cause identified — the upstream file format changed over the weekend. Fix in progress; ETA for data fix is 22:00 HKT tonight. Workaround remains available. Next update in 45 minutes."

⑤ Template C — Resolution update 恢复通报模板

"Resolved 22:40 HKT: the data fix and backfill completed at 22:35; upload service verified healthy with the 23:00 file. All queued transactions have been processed. Post-incident review scheduled for Thursday. Incident INC3345 will be closed after user confirmation."

记住三要素：事实（fact）、时间（time stamp）、下一步（next step + next update time）。没有新进展也要按节奏发 "no change" 更新，让用户安心。

⑥ Status update: say this, not that 状态更新措辞对照

  • ❌ "It's broken again, we're looking into it." → ✅ "File upload is failing for HK users since 09:15 HKT; we are checking the inbound file feed." — specifics beat vagueness.
  • ❌ "We have no idea what's happening." → ✅ "Cause is under investigation; we are reviewing logs for the 09:38 file." — same meaning, professional tone.
  • ❌ "The upstream team broke it." → ✅ "Suspected upstream file format change — confirming with the upstream team."
  • ❌ "It should be fixed soon." → ✅ "ETA for the data fix is 22:00 HKT tonight." — commit to a timestamp, not a feeling.

⑦ On-call first-15-minutes checklist 值班前15分钟行动清单

  • 0–2 min: Acknowledge the page; open/join the incident bridge and the incident channel.
  • 2–5 min: Ask impact + timeframe; check whether the service is fully down or partially degraded.
  • 5–10 min: Rule out the obvious (recent deploy, infra alerts); pull logs filtered on the failing function.
  • 10–15 min: Post the first status update (Template A); agree the update cadence with the incident commander.

⑧ Escalate or not? 上报的判断标准

  • Escalate when: impact is growing, you need another team's action, or the fix needs approval above your level.
  • How to escalate well: facts + what you need + by when — "We need the upstream team to confirm today's file format change by 12:00, or we cannot unblock users."
  • It's not a failure. Escalating early is professionalism, not weakness——汇丰文化里宁可早升级，不要硬扛到 Sev 级别上升。

6. Grammar Notes 语法点

① Present continuous for live incident status 用现在进行时播报现场进展

On a bridge, actions happening right now use the present continuous — it signals "this is in progress as I speak":

  • ✅ "I'm pulling the logs now." / "We're checking the inbound file feed."
  • ❌ "I pull the logs now." — sounds like a habit, not an action in progress.
  • States and facts stay in the simple present: "Status enquiry works fine."

② "Rule out" — evidence-based exclusion 用证据排除可能性

Rule out + noun phrase = 排除某种可能性。Always attach the reason, so your exclusion sounds credible instead of dismissive:

  • ✅ "Last deployment was ten days ago, so I'm ruling out a recent code change."
  • ✅ "We can rule out network issues — other services on the same host are healthy."
  • ❌ "It's probably not the code." — vague guessing without evidence.

③ "I'll…" for decisions made on the spot 用 will 表达现场决策

When a decision is made during the conversation itself, English prefers will over going to:

  • ✅ "If the 11:00 file also fails, I'll escalate to the upstream team." — decided now, live on the bridge.
  • ✅ "I'll post the first status update now."
  • Use going to only for plans already fixed before the call: "We're going to run the backfill tonight anyway."

7. Cultural Tips 文化/职场 Tips

🚨 Status-Update Cadence During Incidents 故障中的汇报节奏
  • Set the cadence and keep it. Say "next update in 30 minutes" and actually deliver — even if the message is "no change, still investigating".
  • Timestamp everything with the timezone (09:15 HKT / 01:15 UTC) — HK, London and KL will all read the same thread.
  • Keep the same channel. Updates go on the bridge / incident channel, not scattered across private chats.
  • Write updates for people who just joined. Someone opens the bridge late — repeat impact and current status, don't just say "as I mentioned".
  • Short > beautiful. Bullet points beat paragraphs when everyone is stressed.
✅ "I don't know yet" is acceptable 说“还不知道”是可以的
  • Saying "I don't know yet, but here's what I'm checking next" sounds professional, not weak — guessing on a bridge is what actually damages trust.
  • Use the 3-part honest answer: "What we know: X. What we don't know: Y. What we're doing: Z."
  • If you truly can't assess yet, say "I need 10 more minutes" with a concrete time — a vague delay is the only real mistake.
  • 中文语境里“我确认一下再回复”很常见；英文直接说 "Let me verify and come back to you in 10 minutes" 同样加分。
⚠️ Avoid Blaming Upstream Teams in Writing 书面沟通避免指责上游团队
  • ❌ "The upstream team broke it again." — incident records are permanent and often quoted in reviews and audits.
  • ✅ "Suspected upstream file format change — confirming with the upstream team." — neutral, factual, verifiable.
  • Describe the system and the change, never the people. Blame in writing travels far and is impossible to take back.
  • 同样的规则适用于中文沟通——口头吐槽可以，落到书面（工单、邮件、频道）永远只写事实。
